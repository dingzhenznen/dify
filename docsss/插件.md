• 在 Dify 里，“插件节点”不是一种单独的通用节点，主要有几类插件相关节点：

  - Tool 节点：调用插件提供的 tool
  - Trigger Plugin 节点：插件触发器节点
  - Data Source 节点：插件型数据源

  你如果问的是工作流里最常见的“插件节点”，核心其实是 Tool 节点；如果是触发型插件，就是 Trigger Plugin 节点。

  前端怎么展示

  前端展示的关键不是写死某个插件，而是根据节点里保存的这些字段动态查元数据：

  - provider_type
  - provider_id
  - plugin_id
  - tool_name / event_name

  Tool 节点组件在：

  web/app/components/workflow/nodes/tool/node.tsx:1

  它会展示：

  - 插件未安装时的 InstallPluginButton
  - 当前 tool 的配置项摘要
  - 缺插件时把节点标记为 _pluginInstallLocked / _dimmed

  具体“这个节点对应哪个插件/工具”的配置解析在：

  web/app/components/workflow/nodes/tool/use-config.ts:1

  这里会根据 provider_type 去不同集合里查：

  - built-in tools
  - custom tools
  - workflow tools
  - MCP tools

  然后再用 provider_id + tool_name 找到当前 tool，拿到：

  - 参数 schema
  - 默认值
  - 认证状态
  - 是否需要授权

  Trigger Plugin 节点同理：

  web/app/components/workflow/nodes/trigger-plugin/node.tsx:1
  web/app/components/workflow/nodes/trigger-plugin/use-config.ts:1

  它会根据 provider_id / provider_name / event_name 找到当前 trigger provider 和 event，再渲染：

  - trigger 的参数表单
  - subscription 状态
  - 未安装插件时的安装按钮

  所以前端展示的本质是：

  1. 节点配置里存插件标识
  2. 前端从插件/工具列表接口拿元数据
  3. 根据标识匹配到当前插件定义
  4. 用定义里的 schema、icon、auth 信息来渲染节点

  后端怎么运行

  ### 1. Tool 插件节点

  后端真正执行 Tool 节点的是：

  api/dify_graph/nodes/tool/tool_node.py:37

  它的 _run() 过程是：

  1. 根据 node data 生成 tool_info
  2. 调 ToolManager.get_workflow_tool_runtime(...) 拿到运行时 tool
  3. 从变量池里解析参数，生成最终 tool_parameters
  4. 调 ToolEngine.generic_invoke(...)
  5. 把插件返回的 message stream 转成工作流事件
  6. 最后产出 NodeRunResult

  关键调用点：

  tool_runtime = ToolManager.get_workflow_tool_runtime(...)
  message_stream = ToolEngine.generic_invoke(...)
  yield from self._transform_message(...)

  也就是说，ToolNode 自己不直接请求插件 daemon，它通过 ToolManager/ToolEngine 这套统一工具运行层来调用。

  而插件型 tool 最终会走到：

  api/core/plugin/impl/tool.py:73

  这里的 PluginToolManager.invoke(...) 会调用 plugin daemon：

  POST plugin/{tenant_id}/dispatch/tool/invoke

  并带上：

  - X-Plugin-ID
  - provider
  - tool name
  - credentials
  - tool_parameters

  所以 Tool 插件节点的真实运行链路是：

  ToolNode._run()
  -> ToolManager.get_workflow_tool_runtime()
  -> ToolEngine.generic_invoke()
  -> PluginToolManager.invoke()
  -> plugin daemon
  -> 返回流式 ToolInvokeMessage
  -> _transform_message() 转成 StreamChunkEvent / StreamCompletedEvent

  Trigger Plugin 节点的执行类是：

  api/dify_graph/nodes/trigger_plugin/trigger_event_node.py:10

  它和 Tool 节点不一样，它在工作流运行时不会再次去调用插件。
  它做的是把“已经由外部触发器带进来的输入”转换成工作流根节点输出：

  node_inputs = dict(self.graph_runtime_state.variable_pool.user_inputs)
  outputs = dict(node_inputs)
  return NodeRunResult(...)

  所以它更像“触发入口映射节点”，不是运行时主动调用插件。

  一句话区分

  - Tool 插件节点：运行时主动调用插件
  - Trigger Plugin 节点：运行时消费已经进来的触发数据
  - 前端展示：都是靠 provider_id / plugin_id / tool_name / event_name 去匹配插件元数据再渲染

  tool、plugin tool、workflow tool 还是 MCP tool。

› 插件是通过http 来调用的吗


• 是，插件调用本质上是通过 HTTP 发给 plugin daemon 的。

  最直接的证据在：

  api/core/plugin/impl/tool.py:73

  PluginToolManager.invoke(...) 最终调用的是：

  self._request_with_plugin_daemon_response_stream(
      "POST",
      f"plugin/{tenant_id}/dispatch/tool/invoke",
      ...
  )

  并且会带这些 HTTP 信息：

  - method: POST
  - path: plugin/{tenant_id}/dispatch/tool/invoke
  - header: X-Plugin-ID
  - Content-Type: application/json

  请求体里会传：

  - user_id
  - conversation_id
  - app_id
  - message_id
  - provider
  - tool
  - credentials
  - credential_type
  - tool_parameters

  plugin daemon 的基础地址来自这里：

  api/core/plugin/impl/base.py:39

  可以看到它用的是：

  - dify_config.PLUGIN_DAEMON_URL
  - dify_config.PLUGIN_DAEMON_KEY

  所以 Dify 后端不是直接在进程内执行插件，而是通过 HTTP 调 plugin daemon 服务，再把 daemon 返回的流式结果转成工作流事
  件。

  补一句区分：

  - 工作流内部节点之间调度，不是 HTTP
  - 插件执行这一步，通常是 HTTP 到 plugin daemon
  - 返回结果还是流式 HTTP response，然后在后端被转成 ToolInvokeMessage
